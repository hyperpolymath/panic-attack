== What the observed startup failures establish

At source `5dfc5c70a74190706312d87343959615ac77484a`, the fourteen
pull-request runs created on 2026-11-04 conclude `startup_failure` and have
empty job lists. For example,
https://github.com/hyperpolymath/panic-attack/actions/runs/41912719217[CI Integrity]
has no job log to inspect. These observations do not identify the platform's
rejection reason. Effective GitHub Actions Settings and the actual startup
diagnostic have not been verified.

There are independently observable source defects. The five Standards callers
now use canonical `metadatastician/standards` coordinates, but their committed
lock entries still name `hyperpolymath/standards@333b06a...`. Three callers
also changed their source pin to `a797d308...`. The tree allowlist omits the
canonical calls, and its former checker discarded both subpaths and refs.
The removed Python generator manufactured native dependency records by
combining old identity fields with newly inferred pins. Those facts require
repair; they do not by themselves prove the cause of all fourteen startup
failures.

The source gates below distinguish immutable references, native coverage,
canonical coordinate identity and offline policy matching. A successful source
check does not certify live admission, billing, or a particular GitHub startup
diagnostic. Missing required contexts remain missing until real runs publish
them; source repairs are not substitutes for those runs.

=== Why `verify.yml` exists at all

Every estate gate except `verify` depends on `hyperpolymath/standards` being
reachable *and* permitted at that instant. That is the right long-term shape -
one place to configure, propagate everywhere - but it means a settings change in
another repository can remove this repository's entire build signal. `verify`
depends on nothing but actions this repository pins itself, so the "does it
compile and pass" answer survives any policy change elsewhere.

[[integrity]]
=== CI integrity

The required job context remains `CI integrity (pins, lock, allowlist, YAML)`,
with the same triggers and read-only repository permission.

SHA pins:: `.githooks/validate-sha-pins.sh` checks external action and
reusable refs. The offline allowlist also requires a complete 40-hex SHA before
matching an external coordinate.

Canonical names:: The unchanged published Standards
`scripts/check-workflow-coordinates.sh` rejects executable former-owner
`hyperpolymath/standards` coordinates, including runtime checkouts.
Historical comments are not executable references.

Native lock coverage:: `.githooks/validate-actions-lock.sh` invokes the
official `gh-actions-lock v0.2.0` binary through the unchanged published
`scripts/update-actions-lock.sh --verify-local`, then
`scripts/check-lock-sync.sh`. The latter checks reusable and local composite
references in both directions. No consumer code emits native lock records.
The gate checks the native executable digest, the exact clean Standards
checkout, a clean consumer commit, and unchanged workflow/lock bytes. Both
checkouts reject assume-unchanged/skip-worktree index flags and ignored inputs;
Git status alone cannot bind hidden working bytes to the recorded commit.

Tree allowlist:: `scripts/ci/check-allowed-actions.sh` parses YAML, resolves
aliases, and reads job/step `uses` values. Owner/repository spelling is
case-insensitive; the complete subpath and ref must match. The five canonical
Standards permissions name only the existing reviewed paths and SHAs.
Existing unrelated patterns are retained. The GitHub-owned flag is respected;
Marketplace verification and effective service Settings are not inferred.

YAML and triage:: Unparseable workflows, invalid ref structures and an empty
input population fail. Printed/commented examples are not executable refs.
The source/API triage reports observations rather than claiming that zero jobs
prove an allowlist failure.

The helper source is
https://github.com/metadatastician/standards/tree/087f6bff5135ce3da6f287c83752256ce4a8efc1[Standards `087f6bff...`].
CI fetches that immutable public commit outside the consumer checkout.
The official Linux amd64 executable is release asset 634768078, with SHA-256
`79ec84c191667fd935a277e6fd3662cf5d3669cccc9e99998731d8f306f373b6`.
The YAML reader is mikefarah yq v4.54.1, release asset 597222595, SHA-256
`8e34fc298390875de416e6a4afcb8cabeceb25d9aa8506c1a2f9353cf702ea5f`.

For local verification, supply absolute paths to the same clean helper
checkout and checksum-matching binary, with yq, jq, Bash and Git available:

==== Temporary process-status adapter

The published helper can promote a valid-looking report even when the native
process exits 2 or higher. The separate upstream repair is tracked in
https://github.com/metadatastician/standards/pull/1394[Standards #1394].
Its unsigned, unqualified candidate is not copied into this consumer.

`scripts/ci/actions-lock-transport.sh` accepts only
`actions-lock --verify-local` and the same command with
`--json=valid,findings`. It invokes the official binary without ambient
authentication or alternate workflow-directory settings. Native exit 0/1 and
their unmodified stdout reach the published helper. For every other exit,
stdout is retained as raw failure evidence but is not offered to that helper
as a reconcilable report. The native status remains nonzero. This adapter
neither parses findings nor changes the published reconciliation rules.

The artifact retains actual stdout, stderr, exit status, consumer commit/tree,
helper revision and executable digest. `not_run` means consumer verification
did not execute; `running` means no native exit was recorded after invocation. A native exit 1 can pass only through the existing canonical
source reconciliation and its actual findings. No report is replaced with an
empty success. This status guard does not claim to repair every upstream
report-shape defect. Remove it after #1394's signed, hosted-qualified fix is
adopted at a reviewed canonical pin.

`scripts/ci/test-ci-integrity.sh` includes exact path/SHA negatives,
quoted/flow YAML controls, deliberately injected valid-JSON/exit-2 and
missing-tool/timeout statuses, malformed reports and unsupported argv.
Those mocked protocol cases are distinguished from the real official
malformed-lock control and from actual consumer verification. Their presence
in source is not an execution receipt; hosted results must record execution.

==== Updating the native lock

Commit the reviewed source change first. Use the existing
https://github.com/hyperpolymath/proven-cicd-and-workflows/actions/workflows/actions-lock-recovery.yml[canonical Actions Lock Recovery workflow]
for `hyperpolymath/panic-attack` at that exact 40-character commit.
Dispatch is a separate authorized operation; `just pins` prints the
candidate SHA and exits nonzero without generating or dispatching anything.

The recovery workflow runs the official binary and the published canonical
`regen_lock` chain in its isolated subject checkout. It restores workflow
bytes and produces a candidate artifact. Before applying that artifact,
verify its exact source identity, actual execution result, canonical lock-sync
result, preserved workflow bytes and native dependency identities. Commit only
the reviewed generated lock after those checks. Reconcile a changed subject
before generating again.

The legacy `action-pins.json` and resolver record historical tag references;
they are not native identity evidence and no longer drive generation.
Do not reconstruct native owner/repository IDs, transitive edges or ref fields,
and do not remove workflow coverage to obtain a passing report.

== Testing: evidence-graded, not declared

`proven/ledger.json` grades this repository's suite on
`proven-tests-and-benches`' 17-category x 14-aspect lattice. The rule the
framework exists to enforce is that **coverage is derived from executed tests,
never declared**, so:

* `scripts/proven/inventory.sh` asks the test runner what tests exist, per
  binary;
* `scripts/proven/verify-ledger.sh` fails when a cell selects no executed test,
  when an executed test is claimed by nothing, or when a stronger tier is
  claimed than the evidence supports;
* the resulting report is fed to `panic-attack aggregate --proven-tests
  --fail-on-defect`, which re-checks the report's internal consistency and fails
  on an unsupported claim (an Actually-Proven entry with no ladder, a cited proof
  file that is not there, a summary that disagrees with the entries).

Tiers are used honestly: this repository has no proof-carrying Rust tests, so
almost everything is `Provisionally-Proven` and says so. Five cells are declared
**absent** with the command that would test them. A declared absence is a to-do
list, not a silencer - `MutationTest` is absent because no mutation campaign
runs here, which is the same `PA025 MutationGap` this tool reports about other
repositories.

== Recon: two analysers, one baseline

`recon.yml` scans this repository with `panic-attack assail` and with
`pons-asinorum` (pinned). They answer different questions - "what here is weak?"
versus "what here is wasted, self-contradictory, or missing an escape hatch?" -
and a finding that appears in both is corroborated evidence while a finding in
exactly one is a prompt to look.

Findings do **not** fail the job. This is the scanner: a scan of its own source
will report what it is built to report, and failing on that creates pressure to
suppress. Instead `recon/baseline.json` freezes the standing counts; a *new*
category or a count *above* baseline fails; a count *below* is reported as debt
paid and should be tightened in the same PR. See
`docs/RECON-AND-EVIDENCE.adoc`.

== Squabbling: fixing stuck gates without bypassing them

`cicd-squabbler` (pinned to a commit) fetches this PR's live gate and reports
which required contexts are missing or stuck, and maps the cross-repo CI chains
this repository depends on. Its invariant is machine-checked: *green if and only
if a required check actually ran and passed*, so an admin override or a dropped
required context are provably not paths to green. It cannot fix code, and does
not try.

Exit codes are part of the contract and are never swallowed:
`0` ok, `2` tool failure (**fails the job**), `3` no required-status-check rule
on the base branch (reported), `4` a blocking chain finding - a cycle or a dead
upstream (reported; fails when `strict` is requested), `5` agent items remain.

== What is deliberately not here

* **No `paths:` filter on a check intended to be required.** A required check
  whose workflow filters itself off does not report as skipped - it does not
  report at all, and the PR waits forever on a context that cannot arrive.
* **No `continue-on-error` on a gate that can disagree with nobody.** An
  advisory job that is always green carries no information; where a check is
  genuinely advisory it says so in its name and its summary.
* **No suppression of a finding to make a gate green.** Where debt exists it is
  frozen in a baseline, in a reviewable file, with the reason.
